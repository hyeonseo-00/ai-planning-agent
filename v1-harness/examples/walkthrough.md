# 파이프라인 흐름 예시 — 가상의 "클래스 예약 취소 화면"

> **이 문서는 형식 예시입니다.** 실제 산출물은 기업 대외비라 공개할 수 없어서, 가상의 클래스 예약 서비스를 두고 각 에이전트 규칙(`.claude/agents/*.md`)의 산출 형식에 맞춰 **직접 작성한 축약본**입니다. 실제 파이프라인 실행 결과가 아닙니다.
>
> 보여주고 싶은 것은 두 가지입니다. ① 단계마다 무엇이 만들어지는지, ② **명세에 없는 값을 AI가 지어내지 않고 `[확인 필요]`로 남긴 뒤, 그중 무엇에서 멈추고 무엇은 넘어가는지.**

---

## 0. 사람의 입력 (`/task`)

```
/task "클래스 예약 취소 화면 프론트 개발해줘. 기획 메모: 수업 시작 24시간 전까지 취소 가능, 취소하면 환불."
```

→ Task Agent가 상위 태스크 `SVA-07`(타입: 프론트개발)을 만들고 `/go SVA-07`을 자동 실행합니다.
→ Orchestrator가 하위 태스크 `SVA-07-1`(명세) · `-2`(화면설계) · `-D`(디자인, 사람) · `-3`(구현) · `-4`(QA)를 만들고 `/spec`부터 이어서 실행합니다.

## 2. 화면설계서 (`/screen` → 3개 파일 + 누락 리포트)

### Layer 1 · 공통 화면 명세 (`3-1_common-screen-spec.md`) — 정책·예외의 단일 기준

```
## [S-01] 예약 취소 확인 모달
- 목적: 사용자가 취소 결과(환불 금액·시점)를 알고 나서 확정하게 한다
- 진입 조건: 예약 상세 > [예약 취소], 수업 시작 24시간 이상 남음
- 정책: 24시간 전까지 취소 가능 / 전액 환불, 원 결제수단, 3영업일 내
- 예외: 24시간 이내 → 버튼 비활성 + 사유 안내 / 네트워크 오류 → [❓ 필요: 재시도 정책]
- 완료 조건: 예약 상태 "취소됨" 반영 + 완료 토스트
```

### Layer 2-A · Design Spec (`3-2a_design-spec.md`) — 디자이너용

```
- UX 의도: 확정 전에 환불 금액과 입금 시점이 스크롤 없이 한 화면에 보인다
- 정보 우선순위: ① 환불 금액 ② 입금 예정일 ③ 취소 후 되돌릴 수 없다는 안내 ④ 버튼
- 시각 강조: 확정 버튼은 Danger 스타일, 닫기 버튼과 크기 동일 (실수 방지)
```

### Layer 2-B · Frontend Spec (`3-2b_frontend-spec.md`) — 구현용

```
Component Tree: CancelConfirmModal > RefundSummary, NoticeText, ButtonGroup(Close, ConfirmCancel)
State: idle → submitting → success | error
Event: ConfirmCancel click → submitting 동안 버튼 disabled (중복 클릭 방지)
Validation: 수업 시작까지 24시간 미만이면 진입 버튼 disabled
API: 예약 취소 — 🟡 mock 대체 (엔드포인트 미정, 결정 주체: 백엔드)
```

> 같은 정책("24시간", "전액 환불")이 Layer 1에만 원본으로 있고, 디자인·구현 명세는 여기서 파생됩니다. 정책이 바뀌면 한 곳만 고치면 됩니다.

## 4. 구현 (`/build`) → QA (`/qa`)

- `/build`: Frontend Spec을 React 코드로 1:1 매핑합니다. Figma와 명세의 컴포넌트 개수·흐름이 다르면(BLOCKER 불일치) 구현을 멈추고 어느 쪽이 맞는지 묻습니다. 정책("24시간", "중복 클릭 방지")은 회귀 테스트(`CancelConfirmModal.policy.test.ts`)로 캡처합니다.
- `/qa`: 기능 ID → Layer 1 → Frontend Spec → 코드 순서로 대조합니다. 하드코딩된 색상이나 API 임의 정의는 T1(즉시 FAIL)로 판정하고, FAIL이면 `/build`를 한 번 자동으로 다시 돌립니다.
